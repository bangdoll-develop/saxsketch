# 領域別偏差（`meshdiff.region_deviations`）の高速化と精度是正

外部編集モデルの「どの部位がどれだけ変わったか」を出す関数の実測記録。
壁時計 30 秒のテストが並行実行で落ちるのを直しに入って、**遅いのは異常系だけで、
正常系は速い代わりに答えが間違っていた**ことが分かったときのもの。

## 着手前のプロファイル（tenor 8026面 / SAMPLE_COUNT=200,000 / WSL2 venv）

`region_deviations` = `_surface_dist` × 2 方向。内訳:

| 段 | 重なるメッシュ | 別座標系（+200,+200 mm） |
|---|---|---|
| `sample_surface` ×2 | 0.04s | 0.04s |
| `cKDTree(200k).query(200k, workers=-1)` | **0.05s** | **5.6〜8.0s** |
| `ProximityQuery.on_surface` 1500点 | 0.18s（0.12ms/点） | **8.2s（5.4ms/点）** |
| **合計（両方向）** | 0.5s | **26〜29s** |

- **KDTree の最近傍は点群どうしが離れていると枝刈りが効かない。** 同一メッシュで
  0.05s、200mm 離すと 5.6s（workers=1 なら 25s）。`distance_upper_bound` を渡すと
  **0.01s** に落ちる。
- `on_surface` が遅いのも同じ理由。trimesh の `nearby_faces` が「最近傍**頂点**までの
  距離」を半径に rtree を引くので、遠い点ではメッシュの全 8026 面が候補になる。
  近い点なら 0.12ms/点で済む。

つまり**遠い点に厳密計算をしていることが唯一の原因**で、遠い点の厳密値は
`DEV_MINOR=0.50mm` の判定に何も足さない（282mm が 282.8mm でも「変化あり」）。

## 同時に見つかった不具合 — 未編集でも「変化あり」が出ていた

旧実装は KDTree の**点対点**距離を基準にしていた。これはサンプル間隔ぶん必ず
過大評価する。tenor の 200k サンプルは間隔 `sqrt(12514mm² / 200k) = 0.25mm`。

```
同一メッシュ（ref vs ref）の点対点距離: 平均 0.125mm  最大 0.514mm
→ 判定: 変化あり 8 ゾーン / 軽微 11 ゾーン / 変化なし 0
```

`_MAX_EXACT=1500` の厳密計算は疑い点から**ランダムに**選ぶ方式で、ゾーン最大値には
まず当たらない。しかも疑い点（`d > 0.12`）は同一メッシュでも **97,308点＝全体の
48.7%** あり、旧コードのコメントにあった「本アプリ由来の編集は疑い点が数百で収まり
上限に当たらない」は事実と違っていた（常に上限に当たっていた）。

## 作り直した測り方（`meshdiff._estimate_dist` / `_exact_dist`）

`trimesh.sample.sample_surface` は `(points, face_index)` を返す。
**最近傍サンプル点が乗っている三角形**を候補にして厳密な点対面距離を取れば、
全点ぶんベクトル化できる。

1. `cKDTree(other_pts).query(pts, k=_CAND_K, distance_upper_bound=_FAR_CAP)`
2. 候補面 `other_face[ii]` へ `trimesh.triangles.closest_point`（`_CHUNK` ずつ）
3. `_FAR_CAP` を超えて `inf` になった点は頂点 KDTree（4千点）の粗い距離で埋める
4. ゾーン統合後、**ゾーン最大値になり得る点だけ** `on_surface` で厳密化

得られる距離は常に真の表面距離**以上**（候補は面の部分集合の min、頂点距離も
表面上の点までの距離）。＝「変化なし」を誤検出しないという安全側の性質は旧実装と同じ。

### 4 の帯の作り方

出すのはゾーンごとの最大値なので、最大値になり得ない点を厳密化しても無駄。
見積りが上界であることを使い、ゾーン `Z` の候補を

```
thr = max(_REFINE_MIN, (Z の見積り最大値) - _EST_TOL)
候補 = { p ∈ Z | thr < d_est(p) < _REFINE_MAX }
```

とする。`d_true ≤ d_est` なので、`d_est ≤ 見積り最大値 − _EST_TOL` の点は
（見積り誤差が `_EST_TOL` 以内である限り）最大値になれない。
`_REFINE_MAX` が**遠い点を厳密化させない**ゲートで、今回の高速化の要。

`_EST_TOL` を外れても、そのゾーンには未厳密化点の見積り値が残る＝過大評価側に
倒れるだけで「変化なし」の誤検出にはならない。

## `_CAND_K` の掃引（tenor 200k点・片方向）

| K | query | 点対面 | 同一メッシュの誤差 max/mean | 0.12mm 超の点数 |
|---|---|---|---|---|
| 2 | 0.10s | 0.13s | 0.246 / 0.0065 | 2258 |
| 4 | 0.10s | 0.45s | 0.211 / 0.0033 | 709 |
| **6** | **0.16s** | **0.68s** | **0.152 / 0.0021** | **363** |
| 8 | 0.17s | 0.96s | 0.152 / 0.0017 | 239 |
| 12 | 0.19s | 1.25s | 0.144 / 0.0012 | 119 |

誤差は `ProximityQuery.on_surface` を真値とした 3000 点の抜き取り。
K を上げると見積りは良くなるが点対面計算が線形に増え、代わりに厳密化する点は減る。
K=6 を採った。`_EST_TOL=0.30` は実測最大誤差 0.152 の約 2 倍。

参考: 三角形の**重心**で KD木を張る素直な方法は**使えない**。この形状は
STL 化のとき平面（テーブル・シャンク端面）が巨大な三角形になり、重心から頂点までが
最大 38mm ある。大きい面に乗った点の最近傍重心が別の小さい面のものになり、
同一メッシュでも平均 0.63mm・最大 6.8mm ずれた。**サンプル点の面番号**なら
面の大きさに左右されない。

## テストの位置づけ

`tests/test_saxsketch.py` 側は**壁時計で速さを測らない**。並行実行で落ちた原因が
それだったので、守りたい性質を不変条件として書いてある:

- `test_region_deviations_foreign_bounded` — `ProximityQuery.on_surface` へ渡る点数が
  **0** であること（＝遠い点は厳密計算経路に入らない）。壁時計 120 秒は
  ハング検知としてだけ残してある。
- `test_region_deviations_identical_is_unchanged` — 上の不具合の回帰ガード。
- `test_region_deviations_matches_known_edit` — +0.30mm がその数字で出ること。
