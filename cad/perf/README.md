# 編集画面の応答性（断面ドラッグ・数値追随・3D再生成）

「丸ポチのドラッグが遅い」「ドラッグが左のスライダーに反映されない」「3D の作り直しが
遅い」「数値・断面・3D が連動していない」という報告を追ったときの実測記録。

原因は 4 つあり、そのうち**3 つは直せて、1 つは直せない**ことが分かった。

## 基準値（着手前 / tenor・step / 静かなマシン）

```
section              med    20.12 ms      ← ドラッグ中に毎フレーム叩かれる。60fps 予算 16ms 超過
simulate             med    19.66 ms      ← パラメータ確定のたび
regions              med     0.02 ms
build                med  4187.93 ms      ← 3D の作り直し
stl                  med   156.36 ms
section_under_build  med   397.83  p95 1226.92  max 2612.04 ms
```

最後の行が本丸。**3D を作り直している最中は断面が 20ms → 400〜2600ms になる。**
`/api/model.stl` は `asyncio.to_thread` に載っているが、OCCT は GIL を離さないので
スレッドでは逃げられない。

## 直したもの

### 1. `profiles.py` の冗長計算（`section` 2.7倍 / `simulate` 2.0倍）

`section()` 1 回が **164,600 回の関数呼び出し**だった。内訳:

```
_pchip             8,285 回  ← 呼ばれるたびに Fritsch–Carlson の係数表を作り直していた
heel_z             8,357 回  ← p だけの関数なのに毎回再計算
outer_radius_nom   7,022 回  （相異なる z は 245 個しかない）
table_plane_y      5,202 回
```

- `_pchip` の係数表をキャッシュ（モジュール定数は import 時に一度、その場で組む
  4〜5 点の表は値キー）。**補間の演算そのものは変えていない**ので同じ入力に
  同じ浮動小数が返る（7 表 × 2001 点でビット一致を確認、テストに固定）。
- `params_scope(p)` の中でだけ効く関数キャッシュ（`_pcached`）。効く条件は
  「スコープに入れた dict と `is` で同一」。`sensitivity()` や `_roof_at()` が作る
  `{**p, k: v}` は別オブジェクトなので**自動的に素通りする** ——
  摂動計算が元の値を拾う事故が構造的に起きない。

### 2. CAD ビルドを常駐ワーカプロセスへ（`build` 中の断面が 36倍）

GIL を分けないと固まりは消えないので、子プロセス 1 本に `build + STL` を投げる
（`saxsketch/server/buildworker.py`）。送るのは
`(instrument_id, template_id, component_id, refs, params, tolerance)` だけ
——`Component.build()` が params の純関数なので親子で状態を持ち合わない。

- 起動は `lifespan` で先に済ませる（build123d の import に 4 秒）。
- 世代番号で古い依頼の結果を読み捨てる。連打しても待ちが直列に積算しない。
- 起動できない／落ちた／90 秒応答しない場合は親プロセスで作る。遅いだけで結果は同じ
  （**STL がバイト一致**することをテストで固定）。
- `spawn` に統一。`fork` だと親が触った OCCT のスレッド状態を引き継いで不安定になりうる。

### 3. フロントの直列化と未確定値

- 確定経路が `250ms → PUT(simulate) → **await の後ろで** 500ms → build` と直列で、
  連続操作のたびに待ちが積算していた。モデルタイマーを PUT と並行に数えるようにした。
- ドラッグ中の値が `SectionEditor` の中に閉じていて、離すまで外に出なかった
  （＝左のスライダーが動かない）。App に `preview` を持たせ、パラメータ欄は
  `{...params, ...preview}` を表示する。サーバ往復ゼロで数値が追随する。
- 断面はドラッグ 1 回につき 2 往復していた（楽観更新 + PUT 応答の 2 回とも
  `params` オブジェクトが変わるため）。PUT 応答は**値が実際に変わったキーだけ**
  取り込むようにした。
- `simulate()` を `_params_key()` でキャッシュ（`_stl_cache` と同じクリア経路）。

### 4. ドラッグ中に図がカーソルの下で跳ねていた（既存のバグ）

実機で測って初めて出てきたもの。同じ画面座標が **mm へ違う値に写っていた**:

```
画面 y を 3px ずつ上へ → mm: -5.28, -5.02, -4.75, -4.48, -6.57, -4.79, -3.68, -5.77
                        値:  2.6,  2.3,  2.0,  1.7,  3.8,  1.7,  0.5,  2.9
```

viewBox は動いていない。**`baffle_warnings()` の件数が値によって増減し、その高さぶん
`.sec-svg`（`flex: 1`）がリサイズされて `getScreenCTM()` が変わっていた。**
掴んだ瞬間の逆行列を固定して解決（`SectionEditor` の `dragCtm`）。
掴んでいる間はレイアウトが動いても写像が変わらない。

これは今回の高速化とは無関係な、断面エディタ導入時からあった穴。「ドラッグの反応が
おかしい」という体感の一因はこれだった可能性が高い。

## 直せなかったもの — `build()` の 4.5 秒

内訳（tenor 既定、静かなマシン）:

```
revolve_profile          0.009s
loft_sections(beak)      0.387s
yz_profile_cut_solid     0.036s
loft_sections(cavity)    0.784s
cut - beak               0.839s
cut - facing             0.152s
cut - cavity             1.455s
cut - bore               0.851s
                        ------
                         4.51s   うちブーリアン 3.30s = 73%
```

試して**駄目だった**もの（同じ道を再び通らないように残す）:

- **ロフト後の向き判定を安くする**（`solid.volume < 0` → トレランス付き
  `VolumeProperties_s`）。負荷が乗った状態で測って「build の 85%」と読み違えたが、
  静かなマシンでは 1 ロフトあたり 0.192s → 0.126s、build 全体の **3%** しかない。
  3 サイズ × 4 型 × ハンドル極値の 60 ケースで符号は一致したが、見返りが小さく
  裏返りのリスクだけ残るので**採用しなかった**。
- **4 回のブーリアンを 1 回にまとめる**。結果は同じ（体積・面数とも一致）だが
  逐次 3.24s に対しリスト一括 4.03s、`Compound` 一括 5.60s と**遅くなる**。
- プレビュー用の低解像度ビルドは、表示形状と造形形状が食い違うのでユーザー判断で不採用。

**cProfile は当てにならない**: `build()` を cProfile で測ると 0.224 秒と出る。
OCCT のブーリアンに入っている時間が計上されないため。壁時計で区間を挟んで測ること。

## 結果（tenor・step）

```
                     着手前        現在        比
section              20.12 ms     7.39 ms    2.72x
simulate             19.66 ms     9.70 ms    2.03x
build              4187.93 ms  4396.42 ms    0.95x   （OCCT のブーリアン。削れない）
stl                 156.36 ms   169.01 ms    0.93x
section_under_build  397.83 ms    11.03 ms   36.08x  ← p95 1226.92 → 34.62 / 最大 2612 → 109
```

`build` が縮まないのは想定どおりで、**その 4.5 秒がもう画面を止めない**というのが
今回の成果。ドラッグ中は数値も断面もサーバ往復なしで追随し、3D は離してから
1 回だけ作り直される。

## 実機での確認（ブラウザ → HTTP → サーバ）

WSL で `python -m saxsketch.server.app` を上げ、断面タブのハンドルを合成ポインタ
イベントでドラッグして測ったもの。

- **左パネルが追随する**: 数値入力もスライダーも
  `2.6 → 2.3 → 2.0 → 1.7 → 1.4 → 1.1 → 0.8 → 0.5 → 0.2 → 0（下限でクランプ）`と
  単調に動く。CTM を固定する前は `2.6 → 1.4 → 3.8 → 1.7 → 0.5 → 2.9` と暴れていた。
- **ドラッグ中に 3D を作り直さない**: 10 回のドラッグ中 `/api/model.stl` は **0 回**、
  `/api/section` が 10 回。離したあと `/api/model.stl` と
  `PUT /api/project/params` が**それぞれ 1 回だけ**。
- **3D 再生成中もドラッグが止まらない**: 4883ms の `/api/model.stl` が飛んでいる間に
  `/api/section` を叩き続けて **n=112 / 中央 16ms / p95 34ms / 最大 326ms**
  （HTTP 往復込み）。着手前は Python レベルですら中央 398ms / p95 1227ms だった。

## 再生成

```bash
wsl bash -lc "PYTHONPATH=. ~/mp_design/.venv/bin/python cad/perf/bench_ui_latency.py --sizes tenor --types step --worker"
```

- `--worker` 無しだと親プロセスでビルドする（＝着手前と同じ経路）。
  `section_under_build` の差でワーカの効果が見える。
- `--json out.json` で保存、`--baseline out.json` で差分表示。
- **他に OCCT を使う処理（`sweep_cad.py` など）が走っていないことを確認してから回すこと。**
  並走させると 10 倍以上ぶれる（この記録も最初はそれで読み違えた）。
