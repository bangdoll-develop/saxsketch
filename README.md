# SaxSketch — 管楽器設計・3Dプリント統合開発環境

サクソフォンを題材に、管楽器とアクセサリ（マウスピース／リード／リガチャー／ネック／本体）を
パラメトリック設計し、設計時の音響シミュレーションを行いながら、3Dプリント入稿データ・
部品表・仕様書までワンストップで生成するローカルWebアプリ。

現在の実装範囲（Phase 0+1）: **サクソフォン マウスピース** の完全な設計〜出力。

## 主な機能

- **パラメトリック設計**: フェイシング（ティップ開き・フェイシング長・カーブ）、バッフル
  （種別・高さ・棚の長さ・段・カーブ量）、チェンバー（スロート断面積比・形状）、ボア、
  ウィンドウ、外形など23項目。各パラメータに音・演奏性への効果を明記。バッフルは
  解説図準拠の**ストレート型／ステップ型／カーブ型**（＋ロールオーバー）を実形状として
  作り分け（既定＝実測 WindyCity のステップ型）。チェンバー断面も4形状
  （ラウンド/スクエア/馬蹄/フラットサイドウォール）を実形状として造形。仕様書に各部名称
  （ティップレール・ランプ・バレル・ウォール等）を掲載。
- **リアルタイム3Dプレビュー**: パラメータ変更 → build123d で形状再生成 → ブラウザに表示。
- **断面エディタ**: ビューアの「断面」タブで中央断面を見ながら、バッフルを**マウスで
  ドラッグして調整**。可動域はサーバ側の形状法則が返すので、形が破綻する値には
  そもそも動かせない（型ごとに有効なハンドルが変わり、型の特徴が保たれる）。
  ドラッグ中は CAD を作り直さない軽量プレビューで即応する。
- **設計時シミュレーション**
  - 音程チェック: 内容積 vs 欠損円錐体積（Benade理論）でセント偏差を推定。
  - 音色レーダー: 明るさ・パワー・抵抗感・柔軟性・エッジを Acta Acustica 2021 の
    知見に基づく回帰モデルで表示。
  - 感度ガイド: 「明るくしたいならこのパラメータを＋」を数値偏微分で常時提案。
  - ゴールシーク: 目標指標からパラメータを逆算（scipy）。差分プレビュー→承認で適用。
  - 音プレビュー: 音色指標から倍音列を合成し Web Audio で即再生。波形＋スペクトル表示、
    A/B聴き比べ。
- **プロジェクト管理**: `.wproj`（ZIP）形式で保存/読込。スキーマバージョン管理・最近使った
  ファイル対応。
- **セット設計（マウスピース一式）**: マウスピースを土台に、リガチャーとリード（任意）を
  **1 つの .wproj** で設計する。セットの中では参照が「生きて」いて、マウスピースを動かせば
  リガチャーもリードも取込み直し無しで追従する。部品タブで切り替え、3D は組んだ位置に
  重ねて表示、出力は 1 フォルダ・仕様書 1 枚・入稿 ZIP 1 本。単体プロジェクト（管体・
  ネックなど）は従来どおり作れる（＝メンバー 1 個のセット）。
- **出力**: STL / STEP / 3MF、部品表(CSV)、仕様書(HTML・断面図SVG付き・印刷推奨条件)、
  入稿パッケージ(ZIP)。オンライン3Dプリントサービスへそのまま渡せる。
  セットでは部品ごとのサブフォルダに分かれ、仕様書と部品表は 1 式で 1 枚にまとまる。
- **外部ツール連携**: FreeCAD / スライサーを設定登録し「開く」ボタンで直接起動。
- **外部編集ワークフロー**: パラメータで表現できない個別調整（名入れ・フィレット・
  スカルプト）を FreeCAD / Blender で行い、アプリに再取込。凍結スナップショット・
  水密検査・領域別偏差・**パラメータ逆算**（編集がどのパラメータをどれだけ変えたか
  自動判定）・陳腐化警告つき。→ [docs/manual-edit-workflow.md](docs/manual-edit-workflow.md)
- **実製作品の検品**: 印刷して届いた実物を測り、設計へ返すための手順。何を・どう測り・
  何と比べるか、**手持ちの計測具で判定に届くかどうか**まで含めて決めてある。
  → [docs/print-inspection.md](docs/print-inspection.md)

## セットアップ

### 前提ソフトウェア

| ツール | 必要バージョン | 用途 | 確認コマンド |
|---|---|---|---|
| Python | 3.11 以上（開発は 3.12 で検証） | バックエンド・CAD・音響計算 | `python --version` |
| uv | 0.11 以上 | Python仮想環境・依存管理（pip より高速） | `uv --version` |
| Node.js | 20 以上（開発は 24 で検証） | フロントエンドのビルド | `node --version` |
| npm | Node同梱 | フロント依存の取得 | `npm --version` |

uv 未導入の場合は [astral.sh/uv](https://docs.astral.sh/uv/) からインストール（Windowsは
PowerShellで `irm https://astral.sh/uv/install.ps1 | iex`）。uv を使いたくなければ
標準の `python -m venv` + `pip` でも代替可（下記「uvを使わない場合」参照）。

### 手順

プロジェクトルート（`pyproject.toml` のあるフォルダ）で順に実行する。

```powershell
# 1) Python仮想環境を作成（.venv フォルダができる）
uv venv

# 2) バックエンド依存をインストール（build123d, fastapi, scipy, trimesh など）
#    -e = 編集可能インストール（ソース変更が即反映）、[dev] = pytest等も含む
uv pip install -e ".[dev]"

# 3) フロントエンドをビルド（frontend/dist/ が生成される）
cd frontend
npm install          # 初回のみ。node_modules を取得
npm run build        # TypeScriptコンパイル + Viteビルド
cd ..
```

各ステップの意味:
- **1〜2**: `build123d`（CADカーネル OCCT）を含むため、初回は数分かかることがある。
  仮想環境 `.venv/` にすべて入り、システムのPythonは汚さない。
- **3**: サーバは `frontend/dist/` を静的配信する。**ここをビルドしないとUIが表示されない**
  （サーバ起動時にトップページが 404 になる）。フロントのソースを編集したら再度
  `npm run build` するか、後述の開発モードを使う。

### uv を使わない場合

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1        # 仮想環境を有効化（macOS/Linux は source .venv/bin/activate）
pip install -e ".[dev]"
cd frontend; npm install; npm run build; cd ..
```

## 起動

### 通常起動（ビルド済みUIを配信）

```powershell
# 仮想環境のPythonでサーバを起動
.\.venv\Scripts\python.exe -m saxsketch.server.app
```

起動すると `http://127.0.0.1:8712` で待ち受ける。**ブラウザでこのURLを開く**と
アプリが表示される（ローカル専用。外部には公開されない）。

- ポートは `8712` 固定（`saxsketch/server/app.py` の `main()` で変更可）。
- 設定ファイルは `~/.saxsketch/settings.json`（外部ツールのパス・最近使ったファイル・
  既定の出力先）。置き場所は `SAXSKETCH_HOME` で差し替えられる（テストはこれで隔離する）。
- エクスポートの既定出力先は `ドキュメント\SaxSketch\`。設定の「既定の出力先」を
  **空にしておくと環境から自動で決まる**。WSLで動かしている場合は Windows 側の
  ドキュメント（OneDrive へリダイレクトされていればそちら）を使う。サーバは Linux 側に
  居るので、`~/Documents` に置くと Windows のエクスプローラからほぼ辿れない。
- 停止は起動ターミナルで `Ctrl+C`。

初回起動時は「新規プロジェクト」ダイアログが開く。楽器=サクソフォン、サイズ=アルト、
コンポーネント=マウスピースを選んで「作成」で設計を開始できる。

### 開発モード（UIを編集しながら使う）

フロントを編集して即反映したい場合は、サーバとViteの開発サーバを**2つ同時に**起動する。

```powershell
# ターミナル1: バックエンド（APIサーバ）
.\.venv\Scripts\python.exe -m saxsketch.server.app

# ターミナル2: フロント開発サーバ（ホットリロード付き）
cd frontend
npm run dev
```

この場合はブラウザで **Viteが表示するURL（通常 `http://localhost:5173`）** を開く。
`/api` へのリクエストは `vite.config.ts` の proxy 設定で自動的に 8712 のサーバへ転送される。
`.tsx` を保存するとブラウザが自動更新される。

### 動作確認

依存が正しく入っているかは、UIを触る前にテストで確認できる。

```powershell
.\.venv\Scripts\python.exe -m pytest tests -q
```

12件すべて green ならジオメトリ生成・音響計算・プロジェクトI/O・APIが正常。

### つまずきやすい点

- **UIが真っ白 / トップページが404** → `frontend/dist/` が無い。`cd frontend && npm run build`
  を実行し忘れていないか確認。
- **`ModuleNotFoundError: saxsketch`** → 仮想環境のPythonで起動していない。`python` ではなく
  `.\.venv\Scripts\python.exe` を使うか、仮想環境を Activate する。
- **`build123d` のインストールが失敗** → Python が 3.11 以上か確認（`python --version`）。
  32bit Python では動かない。
- **ポート 8712 が使用中** → 別プロセスが占有している。`saxsketch/server/app.py` の
  `port=8712` を変更するか、占有プロセスを終了する。
- **エクスポートの「参照」やプロジェクト保存でダイアログが出ない** → その環境では
  OSのファイルダイアログを出せない（またはサーバが手元の画面を持っていない）。
  **代わりにパス入力欄が出る**ので、そこへ直接入力すれば動作する。
  出せるかどうかはサーバが `GET /api/capabilities` の `native_dialogs` で申告する。
- **ダイアログが出たまま操作できない / UIが固まったように見える** → 直っている。
  以前はサーバのプロセス内で tkinter を呼んでいたため、WSLで動かすと Linux 側の
  ダイアログが WSLg 越しに開き、閉じるまで `POST /api/dialog` が返らなかった。
  いまは**必ず別プロセス**で開き、時間切れ（既定 180 秒）とリクエスト切断の
  どちらでも確実に終了させる。WSL/Windows では Windows ネイティブのダイアログを出す。

## 拡張（新しい楽器の追加）

`saxsketch/instruments/<楽器id>/` を追加するだけ。コアは楽器を知らない。

- `descriptor.json` … 楽器の物理定数（調・欠損円錐体積・ネック寸法・リード規格）と、
  セットで組める構成（`sets`: どの部品が必須／任意で、どれが土台か）
- `templates/*.json` … サイズテンプレート（パラメータ初期値）
- `components/` … `Component` 派生クラス（`COMPONENTS` dict で公開）

## アーキテクチャ

- `saxsketch/core/` … スキーマエンジン・プロジェクトI/O（`.wproj` = セット。単体は
  メンバー 1 個）・プラグインレジストリ
- `saxsketch/geometry/` … build123d 共通ビルダー
- `saxsketch/acoustics/` … 音程・音色・感度・ゴールシーク・倍音
- `saxsketch/export/` … モデル/BOM/仕様書/入稿パッケージ
- `saxsketch/server/` … FastAPI
- `frontend/` … React + TypeScript + Three.js（日本語UI）

## ロードマップ

- Phase 2: OpenWind 統合（マウスピースのインピーダンス表示・物理モデル音合成）
- Phase 3: リード・リガチャー（マウスピース外形と自動整合）
- Phase 4-A: 採寸ワークフロー（実物の実測をプロジェクト局所で反映・復元点つき）✔
  - 実物3mf/STLから外形寸法（全長・ボディ径・シャンク内径）を自動測定して採寸へ流し込み ✔
  - 外部編集ツール（FreeCAD）の自動起動（Windows側インストールを自動検出・WSL連携）✔
  - 外部（市販完成品など本アプリ非由来）の3mf/STL/STEPを凍結なしで読込→整列して3D表示・
    外形採寸・入稿STLに登録。差分/逆算はしない（座標系・内部形状が別物のため）。継続編集は
    FreeCADで元ファイルを開いて往復 ✔
  - 別座標系の無関係メッシュを誤取込しても領域偏差計算がハングしないよう厳密計算に上限 ✔
- Phase 4-B: ネック・キーレス管体（トーンホール設計・造形サイズ自動分割）※スライス分割で実装
  - 4-B.1 ネック（円錐ボア＋グースネック曲げ＋オクターブベント。マウスピース適合を
    descriptor 定数で自動検証。ストレート/ベント・ベント有無を選択可。採寸・FreeCAD往復・
    STL/STEP/3MF出力は既存の汎用経路を再利用）✔
    - 正直な範囲: オクターブ**キー機構は非実装**（ベント孔幾何のみ・奏者が塞ぐ/プラグ前提）。
      ボアテーパは直線円錐近似で音程は近似（採寸校正で実物へ寄せる）。長尺の自動分割は 4-B.3。
    - 前方互換: パッド座平坦化＋キー取付ボス（既定OFF）で後段のオクターブキー機構(4-B.4)を
      ネック再設計なしに載せられる。キー機構は印刷剛体パーツ＋購入品（パッド/バネ/軸）で構成予定。
  - 4-B.2 キーレス管体＋トーンホール ※さらに 3 分割
    - 4-B.2a 管体の幾何（円錐管＋ボウ＋ベル＋**ネック一体型**）✔
      - **ネックの繋ぎ方を 2 通り持つ**: `separate`（別体・既定）と `integrated`
        （ネックまで 1 部品）。後者はストレートソプラノに多い実機の作り。
        **音響はどちらでも同じ** —— 共鳴管はマウスピース→円筒ボア→欠損円錐で
        「ネック」という区間を持たないので、継ぎ目もテノンもモデルに入っていない
        （3 サイズで気柱のビット一致をテストで固定）。実利は継手が 1 つ減ること
        （印刷品でいちばん気密が出ないのが継手）。代償は**姿勢を調整できない**こと
        （実機のネックは回して銜え角を合わせる）と、壊れたら全部作り直しになること。
      - **落とし穴**: 「一体型」と「ネック省略」は別物。後者は円錐の先端側が消えて
        soprano +355 / alto +346 / tenor +289 セント上がる＝別の楽器。円錐リーチの
        カードが警告する。
      - 正直な範囲（2a 時点）: **トーンホールは無い**（2b で入った）。**ベルのフレアは 3 サイズとも
        未実測**なので**音響へ接続していない** —— 接続すると全閉の第1共鳴が
        +38〜+106 セント動く（`cad/body/README.md` の測定）。共鳴管は校正済みの
        直線円錐のまま。曲げの音程への影響も未実装（弧長近似）。分割は 4-B.3。
      - **どの構成でも 1 パーツでは印刷できない**（弧長 502〜1378mm）。一体型に
        したから分割が要るのではなく、別体でも要る。
    - 4-B.2a' 後始末: **1 つの楽器に円錐は 1 本**にした ✔
      - ネックだけ `cone_half_angle_deg` の生値を使っており、頂点距離の値を持つ
        **アルトだけ 4.52% 食い違って**いた（別体では継ぎ目の気柱に φ0.56 の段）。
        `neck_profiles` も `volume.missing_cone` を読むようにした。まずいのは
        「アルトが急なこと」ではなく**食い違いが物理ではなくデータの有無で
        決まっていた**こと —— ソプラノに頂点距離が入った日に黙って壊れる規則だった。
        **音響の記録値は 1 つも動かない**（共鳴管はネックの幾何を読んでいない）。
      - **曲げネックの肩が段になっていなかった**（alto 5.6mm / tenor 6.4mm の
        スロープ）。ストレート経路だけが段差の位置を持っていたため、同じ
        パラメータで曲げ角 0 と 24° から違う形が出ていた。肩の定義を 1 か所に。
      - **`missing_cone_length_mm` 217.5 は出典未記録の借り物**と分かった（出所を
        追うと descriptor の一文で終わる）。代わりの半頂角 1.6° も補間なので
        **借り物 A vs 借り物 B**。落としても判定は動かない（アルトの `in_tune_mm`
        13.58→11.58mm、実用域の内側で ok のまま）と測ったうえで**値は動かさず**、
        出所の弱さだけ記録した。決着させる実測は 1 つ —— アルトのネック大端内径
        （予測 φ25.5 vs φ25.0、差 0.56mm）。詳細は `cad/body/README.md`。
    - 4-B.2b 側孔をソルバへ通す（TMM に分岐インピーダンス／OpenWind の
      `holes_valves`）＋管体に穴を開ける ✔
      - **新しい物理ではなく橋渡し。** TMM の分岐行列は OpenWind の
        `JunctionTjoint`（Dubos ら 1999）の質量式を**写した**もの。合っているかは
        文献ではなく OpenWind と突き合わせて測る（`sound_speed()` が `Physics` を
        写しているのと同じ扱い）。**穴を足しても 2 エンジンの差は増えない。**
      - **穴の位置は 0 次規則の暫定値**（開孔位置＝その音が鳴る円錐長）で、
        実測でも解でもない。音階カードが各運指の残差を出す ＝ **4-B.2c の
        ソルバが潰す量**。3 サイズとも**低い側**に外れる（有限径の穴は完全な
        開口端ではなく、ベル寄りの開孔列が実効長を伸ばす）。
      - **記録値は 1 つも動かない。** 穴が無いときは以前とビット一致の経路を通る。
      - **運指ごとの解は 1 回ぶんの費用**。穴の位置が同じなら区間行列は運指でも
        穴径でもチムニーでも変わらないので、`HoleSolver` が使い回す。おかげで
        音階 8 音と感度 2 本が `simulate` の予算（50ms）に収まる。
      - **ここで出た結論 2 つ**（`cad/body/README.md` に数字）:
        (1) **指孔のスパンは音程で決まる**ので「穴を寄せる」ことはできない ——
        全閉から 1 オクターブまでは頂点から測った管の 44.1% で、
        soprano 317 / alto 476 / tenor 637mm。両手（目安 200mm）に**届かない**。
        収まるのは soprano 4 孔 / alto 3 孔 / tenor 2 孔まで＝全閉を入れて
        5 音 / 4 音 / 3 音。**何段まで減らせるかは設計する前に決まっている。**
        (2) **指でふさげる穴径が上限**なので、太いボアの管では開けても十分に
        高くならない。つまり**このサイズでキーレス全音階は成立しない**。
    - 4-B.2c 穴位置を解く（運指表＋指の届く拘束＋チムニー高さで合わせる）。
      2b の結論を受けて、問題設定は「位置を解く」だけでなく**段数を減らす／
      フォーク運指／もっと小さい楽器**の選択を含む
  - 4-B.3 造形サイズ自動分割（軸方向分割＋接合＋ビルドボリューム設定）
  - 4-B.4 オクターブキー機構（印刷剛体パーツ＋購入品BOM）
- Phase 4-C: マウスピース／リード／リガチャーの設計バラエティと寸法表示 ※5スライス

    - **既定の「2点レール」はリードに 1 か所も当たっていなかった。** 4-C.2 で
      リード背面がカマボコになったのに接触面は平面のままで、締め代は中央 0.15 に
      対しレール位置で **0.83〜1.04mm**、全面プレートの端で **1.55〜1.88mm**
      離れていた（剛体バンドが埋められる量ではない）。接触の頂点を `cane_top` から
      起こして、締め代を全 x で `reed_clearance` に揃えた。
    - **接触は別ソリッドではなく内周断面の凸**。材料は「外周 − 内周」なので、
      空洞のタブ床を上へ凸にすればそれが接触要素になる。**ソリッドは常に 1 個**で、
      ブーリアンは増えず、テーブルの 4.18° 傾斜にも自動で従う。線／点は
      サジッタ 0.25mm の丸めた山（半径 2.1mm ≪ リード背面 13.8〜15.2mm なので
      **必ず 1 本の線／1 点**で当たる）。点接触は z 方向にも丸めて前後 2 列。
    - 逆締めは**スリットが必ずタブ床を割る**ので、片持ちの橋（圧力プレート）が
      構造部材として要る。`contact_type="none"` と、橋がバンド厚に収まらない組は
      `params_error` で弾く（3 サイズとも既定は通る。ソプラノは余裕 0.05mm）。
    - 弾性バンドは締め代を**負のはめあい隙間**で表す（下限を −0.60 へ。既定 0.25 は
      可動域の内側）。TPU95A を材料表に追加。**伸びない材料 × ネジなしはカードが
      `bad`**（形としては作れるので `params_error` にはしない）。
    - **旧 `plate_type` の .wproj は変換して 1 行報告する**。`ParamSet` は未知キーを
      黙って捨てるので、フックが無いと「全面プレート」が黙って線接触に変わる。
      `Component.migrate_params`（既定は恒等）を足し、`/api/project` の `notices` →
      警告トーストへ繋いだ。
    - **掃引が既存の穴を見つけた**: テーブル面の「棚」の有無が z で切り替わると
      断面の頂点数が変わり、ルールドロフトの前提が崩れる（弾性 × 負の隙間 × 厚い帯で
      83 と 85 が混在）。円弧の刻みで帳尻を合わせ、pytest にも固定した。
    - 記録値: 既定の体積が **+1.5〜1.7%**（旧レール 16.0mm³ → 新しい線接触
      80.1mm³ ＝ 5.0 倍。alto）。マウスピース・リード・ネック・管体は不変、
      `verify_report.md` は 0 行、音響は無関係。詳細は
      [`cad/ligature/README.md`](cad/ligature/README.md)。

      heel 79mm」から作った公称値で、**「典型的なリガチャーの幅」で座を定義して
      おいて、その座より広いリガチャーを禁じていた**（定義が循環していた）。
    - 直しは後端アンカー: 後端は最大径で止める（そこから先は胴が細るので物理）、

    - **`seat_offset` はもっと死んでいた** —— 可動域 0〜15 のうち生きているのは

      ところで止めたが、**報告しても動かないままだった**（4-D.5 で測り方ごと直した）。

  - 4-C.3c リガチャー: テーパ圧入（ネジなし・通常樹脂） ✔
    - 実物（JodyJazz のネジなし一体リング）と同じ、スリットもネジも無い一体の
      テーパリングを `closure = "taper"` として足した。**伸びない樹脂で成立する。**
    - **荷重の型を 1 度間違えて、測り直して直した。** 最初は「一様内圧でフープが
      伸びる」として計算し「閉じた剛体リングは成立しない・割りスリットが要る」と
      結論した。荷重は真円圧ではなく、**リードが下から・胴が上から押す直径方向の
      2 点** —— 効くのはリングの楕円化で、フープの **1/64〜1/72**（PLA で
      116/119/143 N/mm 対 7400/8603/9897）。押し込み 1mm あたり 8.5〜10.5N。
    - 形は**「`z − press_depth` で引いた輪を `z` に置く」だけ**。円錐とテーブルが
      同じ 1 つのシフトで動くので締め代が 2 か所に分裂しない。**押し込み 0 は
      ネジなしリングとビット一致**、ブーリアンは増えずソリッドは 1 個のまま。

      出し、同時に当てる条件 `clearance ≤ 0.61〜0.68 × reed_clearance` を助言する。
    - 保持力 ÷ 挿入力 = **0.83**（μ と楔角だけで決まり寸法にも材料にも依らない）。
      μ・印刷公差・手で押せる軸力はいずれも**仮定**として明記した。挟み力は
      リングだけの見積りで、実物はリード背面が潰れるぶん**硬め側に外れる**。
    - テンプレートの `closure` は `screw_beak` のままなので**既定の記録値は
      1 つも動かない**。詳細は [`cad/ligature/README.md`](cad/ligature/README.md)。

  - 4-C.5 パラメータの寸法を断面と 3D に図示 ✔（既定オフ）
    - `Component.dimensions(params)`（既定 `[]`）＋ `GET /api/dimensions`。断面は

    - **値は線の両端から測る。** `dimension.dim()` が `value = |b − a|` を計算する

      ので、**黙ったクランプと報告されたクランプがそのまま図に出る**（同じ規則で
      リガチャーの座位置も、飲まれたときだけ実効値と指定値が併記される。
      4-D.5 で測り方を直すまでは、既定でも 実効 0.17 / 要求 4.0 と出ていた）。
    - **`reed_width` は寸法線にしない。** テーブルは平面カットなので実幅は半径と
      カット深さから決まり、z によって変わる（座中央で 13.98 / 15.14 / 14.66mm）。
      `reed_width` が決めているのは窓幅の公称値とリガチャーのタブ幅だけで、
      マウスピースの面を 1 つも決めていない。代わりに実幅を出す。
      **テナーだけ実幅 14.66 < `reed_width` 14.8**（未決着・数字を出すだけ）。
    - 断面へ写せるかは**宣言ではなく座標から導く**（`a.x == b.x == dir.x == 0`）。
      幅方向の寸法は自動的に落ちる。
    - リードの先端の寸法は z=0 に置けない —— 前縁カーブのせいで z=0 の平面視幅は
      0.5mm の刃なので、`tip_full_width_z`（1.86 / 1.85 / 2.19）に置く。
    - `window_length_effective` の docstring の数字を実測で直した（アルトは
      41.1 → **37.9**、全長側は 95.0 → **88.7**。テンプレートが変わる前の値だった）。
- Phase 4-D: マウスピース／リガチャー／リードを**セット**で設計する ※4スライス ✔
  - 4-D.1 セット基盤（`.wproj` v2・部品タブ・生きた参照・単体⇄セットの行き来）✔
    - **1 ファイル = 1 セット。単体はメンバー 1 個のセット**として同じ経路を通る。
      開く/保存/最近使った/凍結/採寸/出力を 2 本に割らないための形で、v1 の
      .wproj は `_migrate()` がメンバー 1 個へ持ち上げる（**そのまま開ける**）。
    - **楽器 ID とテンプレート ID はセットが 1 か所だけ持つ**。メンバーへ複製すると、
      食い違ったときにどちらが正かが**データの有無で決まる**規則になる
      （4-B.2a' の円錐と同じ型の間違い）。セット内は同じ楽器・同じサイズが構造的に保証される。
    - **セット内の参照は「生きて」いる**。従来の参照は取込時点で固定する凍結
      スナップショットで、マウスピースを直すたびに手で取込み直す必要があった。
      セットでは兄弟メンバーの現在値をそのつど束ねる。**無効化の条件を別に書かない**
      —— キャッシュ鍵に束ねた参照が入っているので、マウスピースを動かせば従属部品の
      鍵も変わる。
    - 生きた参照のぶん、**取込操作をしなくても凍結が陳腐化する**（マウスピースを
      触ればリガチャーの外部編集モデルは古くなる）。判定は束ねた参照で見る。
    - どの部品が組になるかは descriptor の `sets` に**データとして**置く（コアは楽器を
      知らない）。管体・ネックのセットを足すときも追記だけで済む。
  - 4-D.2 リガチャーがセットのリードを参照＋セットの適合カード ✔
    - **「リガチャーが挟むリードの寸法」がテンプレート固定だった**（`ligature.py` に
      「リード プロジェクトと同じ .wproj には入らないため」と明記してあった）。
      実際に設計したリードと接触寸法が食い違ったまま作れてしまう状態。いまは
      セットにリードが居ればその実寸、居なければ従来どおりテンプレート。
    - 下流は 1 行も変えていない —— `ligature_profiles` の各関数は最初から `reed_p` を
      引数で受け取っていたので、**出所を差し替えるのは 1 メソッド**で済んだ。
    - **同じ値なら同じ形**をテストで固定（テンプレート値のリードを足しても
      体積・頂点数・断面・寸法がビット一致）。3 サイズとも「テンプレート値」と
      「`ParamSet` を通した既定値」が一致することも固定した —— ここがずれると
      リードを足しただけで形が黙って変わる（`ParamSpec.validate` は黙ってクランプする）。
    - リードの足し引きは**通知に出す**（形が変わることを黙ってやらない）。
    - セットの適合カードは**部品どうしでしか出せない量だけ**を扱う（帯の位置・
      リード全長・削り始め・テーブルの実幅）。各部品の規格照合はそれぞれのカードのまま
      —— 同じ行を 2 か所に置くと、しきい値が散って片方だけ厳しくなる。
    - **テーブル幅は `reed_width` と比べない**。あれは窓幅の公称値でマウスピースの面を
      1 つも決めていないので、`profiles.table_flat_width` の実幅（z で変わる）で見る。
  - 4-D.3 セット 3D（組んだ位置に重ねる）✔
    - **リードだけ座標系が別**（z=0 が先端・y=0 が平らな底面）。テーブルは軸に 4.18°
      傾くので、配置は「X 軸まわりの回転＋平行移動」。**向きも位置も `table_plane_y`
      から測る**（`table_angle` の定数を読まない）——符号を別に決め打つと、平面の定義が
      変わったとき片方だけ直る。
    - 配置は**編集中の部品を基準にした相対変換**で返す。本体を動かすと寸法線も
      影響領域のハイライトも一緒にずれる（どちらも本体のモデル座標で作られている）。
    - 置き場所を宣言しない部品は**出さない**（`REF_SHARES_FRAME` と同じ判断。
      間違った位置に置くより出さないほうが安全）。
    - 正直な範囲: 既定オフ。マウスピースを触ると 3 部品とも作り直しになる
      （5.6〜6.2 秒＋1.3 秒＋リード）。位置関係を見るための表示で、**寸法を測る
      用途には出さない**（リードは先端合わせの理想位置で、実際の銜え位置は奏者が動かす）。
  - 4-D.4 セット出力（1 フォルダ・仕様書 1 枚・入稿 ZIP 1 本）✔
    - 部品ごとに `<部品ID>/model.*`、仕様書と部品表はセットで 1 枚（BOM は先頭列が
      どの部品かを示す）。単体範囲の出力は従来どおりサブフォルダを作らない。
    - 仕様書の本文生成は**単体もセットも同じ関数**（体裁が 2 か所に割れない）。
    - **凍結は部品単位のまま**。外部編集は部品ごとに往復するので、まとめて凍結すると
      触っていない部品まで「編集待ち」になる。陳腐化した部品があればセット出力は止まる。
  - 4-D.5 後始末（ユーザー報告の 4 件）✔
    - **リガチャーを外す経路が無かった**。サーバは外せるのに UI が
      `required`（＝新規セットで最初から作る）を「外せない」に流用していて、× が
      出ていなかった。**1 つの値が 2 つの意味を決める**規則をやめ、外せるかどうかは
      サーバが従属関係で決める（土台は最後に守る）。部品が 1 個に戻ったら
      `is_set` も False に戻す（`set_id` は残すので ＋ボタンで育て直せる）。
    - **リードが常に裏返しに置かれていた**。リードの肉は底面から +y、テーブルの
      外向き法線は −y なので、そのまま置くと肉が丸ごと胴へ潜る（アルトで
      +2.807mm ＝ リード厚 2.800 とほぼ一致）。`assembly_placement` に
      `flip_z` を足した。**一般の 4×4 にはしない** —— `R_x(θ)·F^f`（`F = R_z(π)`）は
      `F·R_x(θ)·F = R_x(−θ)` で**合成が閉じる**ので、相対変換も同じ形のまま書ける。
      これで `(R_x(θ)·F)² = I` ＝ 裏返しが入ると自分自身が逆変換になり、
      「基準を替えると角の符号が反転する」というテストの前提のほうが間違っていた。
    - **座位置オフセットが 98.9% 死んでいた**。座の前端から後ろ向きに測っていたので
      増やすと必ず最大径の壁に当たり、生きているのは 0〜0.17mm、しかも既定
      3.0/4.0/4.5 は壁の外＝どこへ動かしても STL がビット一致していた。
      **最大径から前へ引く量**（`seat_setback`）に測り直して 17〜26mm 全域を生かした。
      **キーごと変えた** —— 値の意味だけ変えると旧値と新値を区別できず、利用者が
      意図して入れた値を黙って 0 に戻す経路ができる。旧 `seat_offset` は
      `migrate_params` が 0.0 へ移し（**形はビット一致**）1 行報告する。
      これは `seat_range` で**2 度目の同じ型**（前回は `band_width`）。
    - **STL/3MF に紋様が出て STEP には出ない**（ユーザーのスクリーンショット）。
      測ったら出所は 2 つで、**片方はメッシュ許容では消えない**:
      周方向は `angular_tolerance` が決めていて 0.3 では 80 角柱（弦誤差 0.0109mm）
      → 0.1 にして 419 角柱（0.0004mm）。母線方向は `revolve_profile` が多角形の
      母線を回すので**ソリッド自体に焼き込まれて**おり、`body_stations` を詰めて
      0.083〜0.133 → **0.026〜0.034mm**。STEP だけ紋様が無いのはスプライン母線だから。
    - **どちらも篏合には効いていなかった**（設計クリアランス 0.25mm・刻み 0.05mm に
      対して 1〜2 桁小さい）。細かくしたのは「見えている凹凸が寸法誤差かもしれない」と
      疑わせないため。**リード密着面はもともと STL と STEP でほぼ同一**（カット断面の
      折れ線が法則から 0.0026〜0.0039mm、最悪点はマウスピースの外側の逃がし区間）。
      母線を詰めた効果は体積差にも出た —— soprano は +0.11% → **+0.003%**。
      alto/tenor は +0.105 / +0.115% でほぼ変わらず、残りは胴ではなく空洞側にある。**測り方の罠**: OCCT は三角形分割を形状に持ち回り linear が
      細かくなったときしか作り直さないので、1 プロセスで許容を振ると angular の
      効きが消えて見える（実際に 1 度誤った結論を出した）。
      `BRepTools.Clean_s` を挟むこと。
  - 4-D.6 「直したのにページが古い」を塞ぐ ✔（ユーザーが同じ .wproj で再報告）
    - 報告は「セット表示でリードが胴の反対側」。**サーバは正しかった** —— 実測で
      `active=mouthpiece` はリード y[−15.414, −7.439]（テーブル側・胴に潜らない）、
      `active=reed` はマウスピースの最大 y が**ちょうど 0.000** で接触は厳密。
      犯人は**ブラウザで動いていた古いページ**で、`flip_z` を落としていた。
    - **3 通り組んで画面と突き合わせて特定した**（リードは本体なので不動 y[0, 2.800]）:

      | | マウスピース y | 軸→リード | 軸→ネジ |
      |---|---|---|---|
      | 4-D.5 以前 | [0.000, 27.041] | −12.12 | +20.71（反対側） |
      | **新サーバ＋旧ページ** | [−25.468, **+2.817**] | **+12.73** | **+22.82（同じ側）** |
      | 正 | [−27.041, 0.000] | +14.92 | −20.71（反対側） |

      旧ページのビーク **+2.817** は 4-D.5 が記録した **+2.807** と同じ数字。
      スクリーンショットの実測比（100 : 170）も旧ページの 12.73 : 22.82 と一致した。
    - **視点に依らない検証量を見つけた** —— リードもネジも軸上（x≈0）なので、射影は
      `y·cos(方位)` で**符号が保たれる**。正しければ**リードとリガチャーのネジは
      必ず軸の反対側**に見える。3D の見た目を疑うときはまずこれを見る。
    - **「潜っていない」だけでは合否を分けられない。** 4-D.5 のテストは接触と貫入を
      見ていたが**左右関係を見ていなかった**ので、旧ページの状態（潜っていないが
      ビーク側に付く）を通してしまう。テーブル平面に対して**肉とビークが反対側**か
      を、3 つの基準すべてで見るテストに替えた。
    - **本当の欠陥は「古いページが黙って動き続ける」こと。** サーバだけ新しい状態は
      エラーを出さず、**それらしく組み上がった絵**を出すので気付けない。殻
      （`index.html`）を `no-store` で配り、資産は内容ハッシュ名なので immutable に
      した。開きっぱなしのタブ用に、`/api/capabilities` が**いま配っている世代**
      （`index-XXXX.js`）を返し、フロントが自分の読み込んだ名前と違えば再読み込みを
      促す。**世代はビルド時に埋め込まず `index.html` の実物から読む** —— 埋め込むと
      「配っている物」と「世代を名乗る値」が別々に古くなれる。
